# 协议说明（咕咕机 / 有道口袋打印机）

三条物理链路、三套报文。本库 `lan.py` / `ble.py` / `cloud.py` 分别实现，字段与算法均
与公开实测记录**逐字节对齐**（见每节末尾的验证）。

---

## 1. 蓝牙（BLE GATT / 经典蓝牙 SPP）—— 本库 `packet.py` + `ble.py`

### 1.1 GATT 拓扑（GT1 实测）

```
service 0000ff00-0000-1000-8000-00805f9b34fb
    chr 0000ff02-...  write   手机 → 打印机
    chr 0000ff01-...  notify  打印机 → 手机
service 0000ff80 / 0000fee7 / 49535343-...（ISSC 透传）/ 0000180a（Device Info）
```

GT1 无配对、无身份校验：扫到即连即打。G4 走 BLE 但公开资料没给 UUID，所以本库
`gatt` 子命令会把整张 GATT 表打出来，让 UUID 自己浮出来（`--ble` 也支持显式传特征值）。

### 1.2 帧格式

```
AA | LEN(2B, little-endian) | CMD(1B) | PAYLOAD | CHECKSUM(1B)

LEN      = 1 + len(PAYLOAD)                      # 含 cmd
CHECKSUM = (0x56 - (LEN_lo + LEN_hi + CMD + ΣPAYLOAD)) & 0xFF
```

等价式 `(0x100 - (0xAA + Σbody)) & 0xFF`（因为 `0xAA + 0x56 == 0x100`），
两份独立资料给出这两种写法，可以互相验算。

### 1.3 CMD

| CMD | 用途 | 备注 |
|---|---|---|
| `0x01` | 读状态 | 50+ 字节响应：电量/版本/SN（SN 在 offset≈35） |
| `0x03` | 控制 | 指示灯、打印浓度、自动关机 |
| `0x04` | 打印 | 文本 / 位图 |

### 1.4 TLV（`TAG(1B) + LEN(2B LE) + VALUE`）

| TAG | 含义 |
|---|---|
| `0x07` | GBK 文本（**每包 ≤300 字节**，超了要分包） |
| `0x08` | 位图分片（≤1024 B，内容为**完整 BMP 文件**的切片） |
| `0x0A` | 数据总长（**官方 SDK 不发**；发了也能被容忍，但默认不发） |
| `0x0B` | 总包数 |
| `0x0C` | 包序号（从 1 开始） |
| `0x0D` | **加粗**（1 字节，0/1） |
| `0x10` | **字号档位**（1 字节，0=普通 1=大 2=更大；不是像素字号）。<br>**注意：GT1 实测该档位可能被固件忽略** —— 需要真实字号变化请走位图（BMP）路径 |
| `0x11` | **下划线**（1 字节，0/1） |
| `0x12` | 其它样式位 |

> 实机验证：文本帧必须带 `0x0D`/`0x11`/`0x10` 这三个样式 tag（哪怕值都是 0），
> 否则固件行为不可预期（实测会出现奇怪的替换字形）。只发 `0x0B`/`0x0C`/`0x07` 不够。

### 1.5 发送要点

* 打印前先发 **2×1024 B 的 0x00 预热**（部分固件必需）。
* 位图必须**连发、不等逐包 ACK**；逐包等会踩 3 s 超时 → 不出纸。
* 位图需 `FLIP_TOP_BOTTOM`（本库在 `raw_to_bmp(top_down=True)` 与裸位图行序里统一处理）。

### 1.6 验证

文档给的三条真实报文，用本库生成后**逐字节一致**（`python -m memobird_printer selftest`）：

| 场景 | 期望报文 |
|---|---|
| 开指示灯 | `aa 05 00 03 03 01 00 01 49` |
| 读状态 | `aa 01 00 01 54` |
| 打印头（总包/包序/总长 3 个 TLV） | `aa 10 00 04 0b 02 00 05 00 0c 02 00 01 00 0a 02 00 29 00 ec` |

手算第三帧：`Σpayload = 18+15+53 = 86`；`body = 10 00 04 + payload` → `Σbody = 106`；
`0x56 - 106 = -20 → &0xFF = 0xEC` ✓

## 1.7 设备信息与设置（cmd 0x01 / 0x02 / 0x03 / 0x09 / 0x0A）

真机（GT1 `00:15:83:E4:7A:F2`）实测，2026-11-17：

| cmd | 作用 | 回包 |
|---|---|---|
| `0x01` | 读状态（详版） | `cmd=0x01`，83 B，比 0x02 多一个 `0x14`(8 B) |
| `0x02` | 读状态（简版） | `cmd=0x02`，72 B |
| `0x03` | **写设置**（tag=设置项, value=值） | `cmd=0x03` + `0x0E=1` 应答，随后设备主动推 `0x0A` 状态 |
| `0x04` | 打印 | 23 B ack（`0x0B`=总包数 `0x0C`=包序） |
| `0x05` / `0x06` / `0x07` | **设置类（回显参数）** | 发 `cmd 0x05 payload=14` → 回 `aa 04 00 05 14 00 00 39`（值原样带回，补成 3 字节）。⚠️ 三个各写 20 后**指示灯由绿变白**（疑似 RGB 三色通道）；再写 255 后设备**仍在广播却拒绝连接**，需断电重启 → 未摸清前**别写这三个命令** |
| `0x08` | 未明 | 回 `0x0E=1`（与参数无关） |
| `0x09` | 读序列号 | 40 B，只有 `0x0F`(32 B ASCII) |
| `0x0A` | **设备主动上报状态** | 同 0x02 的 72 B 帧 —— 不是谁的应答，是推送 |

状态 TLV（三种状态帧共用）：

| tag | 实测 | 结论 |
|---|---|---|
| `0xFF` | `01` | 固定 |
| `0x01` | `23` | **恒定值**：充电 5 分钟、打满黑页、捂热电池、写入 30 —— 全都不变 ⇒ 不是温度也不是电量，更像固件常量（或永不更新的"假电量"） |
| `0x02` | `10` | **打印浓度（1..10，默认 10）** ✅ 写 3 明显变浅。浓度越低 → 每行加热越久 → 打印越慢；慢速 BLE（~3 KB/s）下**反而能完整打完长图**（默认 10 时约 25 mm 就断粮）。重启后读到 7，说明该值可能被持久化 |
| `0x03` | `00/01` | **指示灯开关**（写 1 灯亮、写 0 灯灭，状态同步）✅ 因果已验证 |
| `0x04` | `80/81` | **电池电压**（0.05 V/LSB）：未充电 74(3.70 V)、插电充电后 79~80(3.95~4.00 V)、负载时下掉 ✅ 可据此估算电量（±10%） |
| `0x05` | `01` | 只读状态位（恒为 1，未观察到变化） |
| `0x06` | `00/01` | **缺纸标志** ✅ 双向验证：00:24:39 抽出纸 `0→1`（同时状态灯变红）、00:28:57 放回 `1→0` |
| `0x0F` | 32 B ASCII | **序列号**（实测 `636404963750000000`） |
| `0x13` | `F0` → `1E` | **不是常量**：断电重启后由 240 变 30 ⇒ 含运行状态位 |
| `0x14` | 8 B | 仅 `cmd 0x01` 有；读到过 `0`、`4672`、`2280` ⇒ 疑似累计计数/计时 |

**踩坑记录（两个都踩过）**：

1. **通知会被拆片**：设备可能把 83 B 的回包拆成多个 20 B 通知 → 必须按 `AA/LEN` 重组，
   否则只能拿到半截帧（现象：`[无法解析] 39 36 33 37 …`）。
2. **订阅后的第一包是上次连接的残留**：刚 `start_notify` 上来会先收到旧分片，
   把正常应答挤掉 → 每次发送前清空缓冲、失败重试。

另外：这台机器的**标准 GATT 设备信息服务（0x180A）是蓝牙模组的，不是打印机的** ——
读到的是 `ISSC / BT5050 / 5050_SPP / 2030030`（透传模组的厂商与固件版本）。
**没有 0x180F 电池服务**，所以电量只能从厂商协议的 `tag 0x01` 拿。

### 1.9 走纸：怎么打出"指定长度"

打印头 **203 dpi = 8 点/毫米**（1 点 = 0.125 mm）。有两档精度：

| 方式 | 精度 | 做法 | 代价 |
|---|---|---|---|
| **空白位图** | 精确到点（±0.125 mm） | 打一张 384×N 的全白位图，纸就被送出去 N/8 mm | 19 帧 / ~19 KB 走 50 mm（帧数按高度线性增长）|
| 换行文本 | 粗（一行 = 固件字高） | 文本帧里塞 N 个 `\n` | 1 帧几字节，极省 |

要点：

* 全白图**不显色但纸照样走** —— 这是唯一能精确控制长度的手法；
* 个别固件会把"整幅全白"当作没内容而跳过，遇到就加 `tick`：在第 1 行画 1 个黑点
  （肉眼几乎看不出）即可触发走纸；
* 实测校验方法：打一张「黑杠 + 50 mm 空白 + 黑杠」的标定图，用尺量中间空白。

**单任务上限（实机二分）**：GT1 一个打印任务最多能完整打出约 **400 行（50mm / 19.2KB）**。

| 高度 | 载荷 | 结果 |
|---|---|---|
| 320 行（40mm） | 15.4KB | ✅ 完整 |
| 400 行（50mm） | 19.2KB | ✅ 完整 |
| 480 行（60mm） | 23.1KB | ❌ 只打出开头 1mm |

超过就必须分页（`paper.paginate` / 网页的 `paginateRaw`，每页 ≤400 行）。
**分页已验证**：480 行的刻度尺分 2 页（400 + 80）打出来，两页内容都完整，
页间空隙实测 18~19mm（就是固件那个固定值）。
注意这与"帧数"无关：把每帧载荷从 1024 提到 4096（23 帧→6 帧）仍然失败。

**长图打印建议浓度 5~6**：默认 10 太快，慢速 BLE 供不上会断在约 25 mm；
5~6 既能打完整、颜色也不至于太浅（软件侧还能用 darken 补偿）。

**固件固定多喂的纸（重要！）**：GT1 每个打印任务都会额外送 **11 mm（任务开始）+ 7 mm（任务结束）= 18 mm**，
与内容无关（实测：40 mm 内容 → 58 mm 纸；12 mm 内容 → 上 11 / 下 7）。

所以：

```
出纸总长 = 内容高度 + 18 mm
```

要一张 40 mm 的纸，内容只需画 22 mm：`--total-mm 40`。要内容本身 40 mm：`--length-mm 40`（总长会是 58 mm）。

> ⚠️ **待实测**：这 18 mm 是在**打印任务**上量的。纯走纸（全白图）是否也有同样的 18 mm
> 还没验证 —— 网页端「走纸」按钮已改成按纸总长算（`blankJob(mm,{total:true})`），
> 如果实测发现走纸没有这 18 mm 开销，就把 `total:true` 去掉。

### 1.10 让整张纸正好 N 毫米（和"走纸"不是一回事）

| | 含义 | 实现 |
|---|---|---|
| **走纸 feed** | 打完后**额外**再送 N mm 空白 | `POST /feed {"mm":20}` / `feed --mm 20` |
| **整页长度 lengthMm** | 让内容 + 补白后的**出纸总长**正好 N mm | `POST /print {"text":"...","lengthMm":60}` / `--length-mm 60` |

因为"出纸总长 = 位图高度"，所以整页长度必须靠**补白/裁切位图**实现：
内容 47 点 + 补到 480 点 ⇒ 出纸正好 480/8 = 60 mm。补白位置可选 top/center/bottom。

### 1.8 关于电量：这台机器给不出来

拆开看电池是**三线**（黑 GND / 红 V+ / 黄 NTC）—— 有热敏电阻、**没有电量计芯片**。
按道理温度应该有读数，但 `0x01` 对以下刺激全部无反应：

| 刺激 | `0x01` |
|---|---|
| 充电 5 分钟 | 23（不变） |
| 打满黑页（打印头满载） | 23（不变） |
| 用手捂热电池 / 吹热气 | 23（不变） |
| 写入 30 | 23（拒绝） |

**但 0x04 是电池电压**（0.05 V/LSB）：实测未充电 74(3.70V) → 插电充电后 79~80(3.95~4.00V)，负载时下掉。所以**电量可以由电压估算**（±10%，负载时偏低），见 `device.battery_percent()`。

结论：固件不提供直接的电量/温度读数，电量只能**由电压估算**。唯一会动的是 `0x04`（电压类），
可以看趋势（负载重不重），但给不出百分比 —— 除非做满电↔空电标定。

> 附注：`0x04` 在 80/81 之间抖动，不只是打黑页时会掉 —— 频繁 BLE 连接（射频活动）
> 也会让它掉到 80。这进一步支持"它是电压类读数"，而不是百分比。

工具：

```bash
python -m memobird_printer info    --ble <地址> [--json]     # 人读/JSON
python -m memobird_printer setting --ble <地址> --tag 0x03 --value 1   # 开灯
python tools/bt_probe.py full <地址>                        # 一次连接读全部 + 扫命令
python tools/bt_probe.py watch <地址> --count 4 --interval 10   # 观察哪些字段在变
```

## 2. 局域网 HTTP —— 本库 `lan.py`

WiFi 机型在同网段暴露 `http://<ip>/sys/printer`（端口 80）。**不需要 ak、不需要绑定、不需要 root。**

### 2.1 状态

```
GET http://<ip>/sys/printer
→ {"command":5,"printerState":3,"busy":0}
```

### 2.2 打印

```
POST http://<ip>/sys/printer
Content-Type: application/json

{"command":3,
 "content":{"textList":[{"encodeType":0,"printType":1,"basetext":"SGVsbG8K",
                          "fontSize":1,"bold":0,"underline":0}]},
 "encryptFlag":0,"hasHead":0,"hasSignature":0,"hasTail":0,
 "isFromDirectPrint":false,"msgType":1,"pkgCount":1,"pkgNo":1,
 "printID":123456,"priority":0,"result":0,"scripType":3}
```

| 字段 | 取值 |
|---|---|
| `printType` | `1` 文本，`4` 图标/贴纸（`iconID` 41 粗线 / 42 细线 / 43 虚线），`5` 图片 |
| `basetext` | `printType=1` → **base64(GBK 文本)**；`5` → base64(**1bpp、384 宽、垂直翻转的 BMP**) |
| `fontSize` | `1` 正常，`2` 大字 |
| `printID` | **每单必须新值**；重复会被静默丢弃（本库用毫秒时间戳生成） |
| `pkgNo`/`pkgCount` | body >≈26 KB 时固件回 500，需同一 `printID` 分包 |

已知坑：G2 用图片任务可能出白纸，只稳定支持文本（社区实测）。

## 3. 云端开放平台 —— 本库 `cloud.py`

官方《WebAPI》PDF v0.5（2017-11-21）<http://open.memobird.cn/upload/webapi.pdf>。
**没有 sign**，系统级参数只有 `ak` + `timestamp`（`YYYY-MM-DD HH:mm:ss`，空格需 `%20`，
服务端不校验时效）。流传的 `sign=sha1(ak+timestamp)` 在官方文档与 6 个主流 SDK 里都不存在。

| 用途 | 路径 | 参数 | 返回 |
|---|---|---|---|
| 绑定 | `/home/setuserbind` | `ak`,`timestamp`,`memobirdID`,`useridentifying` | `showapi_userid` |
| 下发打印 | `/home/printpaper` | `ak`,`timestamp`,`printcontent`,`memobirdID`,`userID` | `printcontentid` |
| 查状态 | `/home/getprintstatus` | `ak`,`timestamp`,`printcontentid` | `printflag`（1=已打印） |
| 图转单色 | `/home/getSignalBase64Pic` | `ak`,`imgBase64String` | `result`（BMP b64） |
| 打 URL | `/home/printpaperFromUrl` | `ak`,`timestamp`,`printUrl`,`memobirdID`,`userID` | 同上 |
| 打 HTML | `/home/printpaperFromHtml` | `ak`,`timestamp`,`printHtml`,`memobirdID`,`userID` | 同上 |

* `memobirdID`：16 位十六进制设备号（双击设备打印出来的编号）。
* `userID`：只能由 `setuserbind` 的 `showapi_userid` 得到。
* `printcontent`：`T:<base64(GBK 文本)>` 或 `P:<base64(1bpp BMP)>`，**多条用 `|` 连接**。
  汉字必须 GBK 再 base64（UTF-8 会乱码）。
* `ak` 需要注册"咕咕开发者"或邮件申请；已绑定到别的账号的机器，`setuserbind` 常报
  `咕咕机未激活或者未绑定` —— 所以这条路只作兜底。

## 4. 打印位图规格（三条路径共用）

| 项 | 值 |
|---|---|
| 打印头宽度 | **384 dots**（G4 虽然 300dpi，仍按 384 点宽送图） |
| 纸宽 | 57 mm |
| 位深 | 1 bpp，MSB 在左，行按字节对齐（384/8 = 48 B/行） |
| 黑色 | bit = 1 |
| BMP 要求 | `planes=1`、`bpp=1`，**`biHeight` 取正、但像素行按 top-down 顺序写入**（官方 SDK 的"非标准 BMP"），否则固件不认 / 打不出图（实测打出自带的 "nice to meet you" 示范页） |
| 灰度映射 | 抖动可选 Floyd-Steinberg / Atkinson / Bayer / 纯阈值 |

### 4.1 为什么必须发 BMP，不能只发像素

`tag 0x08` 的载荷是**完整 BMP 文件**的切片，不是裸像素：

| 方式 | 载荷 | 结果 |
|---|---|---|
| **BMP 文件帧** | 14B 文件头 + 40B 信息头 + 调色板 + 像素 | ✅ 宽高/位深/调色板都在头里，固件照着解 |
| 裸位图帧 | 只有像素字节 | ❌ GT1 不收：固件不知道宽高（实测不出纸） |

裸位图选项已从界面移除（GT1 实测不出纸）；`packet.build_bitmap_job()` 仍保留在库里，
仅供给"按包数推算尺寸"的少数固件做实验。发 BMP 是唯一可靠路径。

本库 `raw_to_bmp()` 生成的就是这个格式，已用标准解码器（PIL）回读并**逐像素比对通过**。
